# EmDash 1.1: re-evaluating the gate

> **Read with ADR-0001 (2026-10-13).** This note judged EmDash against the git-content gate and the "no content database" lock. ADR-0001 retired both. The "not met" verdict and the SQLite conflict in §3.3 no longer disqualify EmDash: it is a candidate for ADR-0002. Its fit findings (§3) still stand.

Research note, 2026-10-05. Facts only, with no recommendation. The question is whether EmDash, ruled out on 2026-08-30 at 0.35.0, now passes its re-evaluation gate. The gate reads: *"Re-evaluate only when both are true: 1.0 shipped, and a documented git-sync or file-based content story exists."*

- Every claim below was checked against the linked primary source on 2026-10-05 *(verified 2026-10-05)*. Anything that is not verified is marked *unverified*.
- `E/…` means the EmDash repo at tag `emdash@1.1.0`, SHA `913cb1bb9b7f08c3ff0d258b4420e53835b6a58e`. Links use `https://github.com/emdash-cms/emdash/blob/913cb1b/…`.
- `main@6ce73ad` means the EmDash `main` branch at `6ce73ad80d9ff0fa65f7d9c76a5373da26d089c8`, the 2026-10-05 HEAD.

Nearest file-shaped mechanisms. None of them is a git-sync story.

- **Seed files.**
  - `emdash export-seed --with-content` writes a seed file, and `emdash seed --on-conflict skip|update|error` applies one ([E/reference/cli.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/reference/cli.mdx)).
  - The docs describe seeds as "intended for first setup and explicit seed commands, not as a migration that runs on every deployment" ([E/themes/seed-files.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/themes/seed-files.mdx)).
- **Site packages (`.emdash`).** These are one-way transfers into an empty site, added in 0.40.0 by [#3346](https://github.com/emdash-cms/emdash/pull/3346) ([E/guides/site-transfer.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/site-transfer.mdx)).
- **CLI Markdown round-trip.** CLI and client reads return Markdown, and writes convert Markdown to Portable Text (§3.8). This is a conversion layer only. Storage is still SQL.

The Cloudflare blog says EmDash Build "tracks every change as a git commit". That describes the alpha AI site-builder sandbox, not EmDash content storage: on publish, "the content moves into a production EmDash site" ([blog.cloudflare.com/emdash-cms-plugin-registry](https://blog.cloudflare.com/emdash-cms-plugin-registry/), 2026-09-28).

## 3. Fit against the stack *(all bullets verified 2026-10-05)*

### 3.1 Node self-hosting vs Cloudflare-only features
- **Node is a supported target.**
  - It needs Node 22.16 or later. Single-server setups use SQLite plus local media storage; the docs include a Docker example with a volume ([E/deployment/nodejs.mdx L8-12](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/deployment/nodejs.mdx#L8-L12)).
  - Disk must persist: "Ephemeral filesystems will lose your database on restart" (L230).
  - The built-in scheduler, which handles scheduled publishing, "runs only while a Node.js process is running" (L69-71).
- **Cloudflare-only features.**
  - The Cloudflare blog lists "optional KV object caching, Hyperdrive database adapter, and Workers Cache compatibility". The 1.0 post says: "all features work anywhere that you can deploy Node.js apps" ([emdashcms.com/blog/emdash-1-0](https://emdashcms.com/blog/emdash-1-0)).
  - The Cloudflare Access auth mode is Cloudflare-only and exclusive ([E/guides/authentication.mdx L12](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/authentication.mdx#L12)).
  - Node uses an in-memory object cache instead of KV ([E/deployment/object-cache.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/deployment/object-cache.mdx)).
- **Sandboxed plugins.**
  - On Cloudflare they need the **Workers Paid plan** plus a `worker_loaders` binding.
  - On Node they need only the `workerd` package, through `@emdash-cms/sandbox-workerd`.
  - On Node only wall time is enforced; CPU and subrequest limits are not ([E/deployment/plugin-sandbox.mdx L10-23](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/deployment/plugin-sandbox.mdx#L10-L23)).

### 3.2 Integration shape, routing, and live collections behind our middleware
- **EmDash is an Astro integration inside our app, not a separate service.** "Astro still controls routing, layouts, rendering, styles, and the deployment adapter" ([E/coming-from/astro.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/coming-from/astro.mdx)).
- **Injected routes.**
  - It always injects `/_emdash/*` (admin and API) and `/.well-known/oauth-protected-resource`.
  - It injects `/sitemap.xml`, `/sitemap-[collection].xml` and `/robots.txt` only if the project does not define them ([E/packages/core/src/astro/integration/routes.ts L850, L1030-1050](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/astro/integration/routes.ts#L1030-L1050)).
- **Middleware.**
  - EmDash registers six middlewares, or seven with `middleware.outer`, all `order: "pre"`, so they run before our `src/middleware.ts`. They are: optional `middleware.outer`, runtime, redirect, setup, auth, media-usage-write-fence and request-context ([E/packages/core/src/astro/integration/index.ts L336-385](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/astro/integration/index.ts#L336-L385)).
  - On non-`/_emdash` routes, the auth middleware does a "soft auth check (set locals.user if session exists, but never block)" ([E/packages/core/src/astro/middleware/auth.ts L190, L245](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/astro/middleware/auth.ts#L245)).
  - The redirect middleware may answer public paths from redirect rules stored in the database; it skips `/_emdash` and `/_image` ([E/…/middleware/redirect.ts L27-50](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/astro/middleware/redirect.ts#L27-L50)).
  - Our middleware still runs for page routes. Whether it can veto EmDash's own `/_emdash/api/*` public endpoints, such as `search`, was not tested (see §6).
- **Reading content.**
  - Content is read through Astro **live** collections (`emdashLoader`, `getEmDashCollection`, `getEmDashEntry`) at request time ([E/why-emdash.mdx L19](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/why-emdash.mdx#L19)).
  - Existing file-based collections stay separate: "EmDash does not copy file-based entries into its database" (coming-from/astro.mdx).
- **Further requirements.** EmDash needs a React integration and a configured Astro session driver; it warns if no session driver is set (integration/index.ts L719).

### 3.3 Database requirement and source of truth
- **A database is required.** Supported databases: SQLite (Node, persistent disk, WAL, not over NFS), D1, PostgreSQL, libSQL, and Hyperdrive (Workers).
- **It holds everything.** "The database holds the content model, entries, users, settings, and plugin data" ([E/deployment/database.mdx L8](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/deployment/database.mdx#L8)).
- **The database is the source of truth.** "The database remains the source of truth" ([E/deployment/object-cache.mdx L10](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/deployment/object-cache.mdx#L10)).
- **This conflicts with two locked decisions.** It contradicts "git is the content bus; no content database", and adding a database is a stop condition.

### 3.4 Editor authentication (Staff and Club Leads)
- **Built-in methods.**
  - Passkeys come first.
  - Optional providers are GitHub, Google, and Microsoft. Microsoft is new in 1.1.
  - Atmosphere (AT Protocol) is a separate package ([E/guides/authentication.mdx L10, L95-211](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/authentication.mdx#L95)).
- **No Discord or generic OIDC provider** ships. `packages/core/src/auth/providers/` contains only github, google and microsoft. Searches of issues and discussions for "discord" and "oidc" returned nothing relevant.
- **Custom provider: the documented path.**
  - The docs offer "Build a provider" using `AuthProviderDescriptor` ([L233-257](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/authentication.mdx#L233-L257)).
  - The reference implementation is `auth-atproto`, which calls `findOrCreateOAuthUser(…, async () => ({allowed, role}))` ([E/packages/auth-atproto/src/routes/callback.ts L140-170](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/auth-atproto/src/routes/callback.ts#L140-L170)).
  - That provider generates **synthetic emails** (`did…@atproto.invalid`), so a provider does not need real editor emails.
  - The role is assigned only when the user is created; a linked account comes back unchanged ([E/packages/auth/src/oauth/consumer.ts L353](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/auth/src/oauth/consumer.ts#L353)). Keeping roles in sync with Discord roles would be our code. That is an inference from the source, not a documented behaviour.
- **Transparent `auth` adapter: the undocumented path.**
  - An `AuthDescriptor` provides `authenticate(request) → {email, name, role}` on every request. The type comment names "okta", "auth0" as examples ([E/packages/core/src/auth/types.ts L17-70](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/auth/types.ts#L17-L70)).
  - It is documented only for Cloudflare `access()`.
- **No GitHub accounts are needed.**
- **Email is optional.** Invites fall back to "copy the generated link" when no email provider is configured. Magic links need an email provider plugin ([L52, L75, L291](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/authentication.mdx#L291)).

### 3.5 Authorization
- **Five fixed roles.** Subscriber 10, Contributor 20 ("needs approval to publish"), Author 30 ("Create/edit/publish own content"), Editor 40, Admin 50 ([authentication.mdx L259-269](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/authentication.mdx#L259-L269)).
- **Own-only scoping exists.**
  - `content:edit_own` and `publish_own` belong to Author; `edit_any` and `publish_any` to Editor ([E/packages/auth/src/rbac.ts L19-35](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/auth/src/rbac.ts#L19-L35)).
  - Ownership is the entry's `authorId`, and only Editor or above may change `authorId` ([E/…/routes/api/content/[collection]/[id].ts L102-132](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/astro/routes/api/content/%5Bcollection%5D/%5Bid%5D.ts#L102-L132)).
  - An Editor can therefore assign an entry to a Club Lead who holds the Author role.
- **Limits.**
  - There are no per-collection permissions and no custom roles.
  - Only one owner is stored per entry: one `authorId`. The source shows no field for co-owners. *(unverified: no explicit doc statement either way)*

### 3.6 Visual editing, markdown input, full-text search
- **Visual editing.**
  - Inline editing works through `{...entry.edit.title}` annotations ([E/reference/api.mdx L251](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/reference/api.mdx#L251)).
  - Authenticated editors get a floating toolbar ([E/guides/preview.mdx L235](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/preview.mdx#L235)).
  - The docs add: "not a visual page builder" ([E/why-emdash.mdx L24](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/why-emdash.mdx#L24)).
- **Markdown input.**
  - The Portable Text editor is a WYSIWYG editor.
  - A separate `richText` field kind takes raw Markdown in a textarea (§2, row 1).
  - Custom blocks have no Markdown form: "Tier 2: EmDash custom blocks <-> Markdown directives (future)". Unknown blocks become opaque HTML-comment fences ([E/packages/core/src/client/portable-text.ts L2-7](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/client/portable-text.ts#L2-L7)).
- **Full-text search.**
  - Full-text search covers fields marked searchable, and is exposed at `/_emdash/api/search` ([E/concepts/collections.mdx L45, L93](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/concepts/collections.mdx#L45)).
  - It works **only on SQLite and D1**, not PostgreSQL ([E/guides/site-transfer.mdx L480](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/site-transfer.mdx#L480)).

### 3.7 Licence and cost
- **Licence.** EmDash is MIT ([repo metadata](https://github.com/emdash-cms/emdash)) and has no paid tier.
- **Hosting cost.** On Node the extra hosting cost is a persistent volume on the existing Railway service.
  - Railway charges "$0.15 / GB / month" for volumes.
  - Hobby allows 5 GB per service and includes "$5 of resource usage per month" ([docs.railway.com/reference/pricing/plans](https://docs.railway.com/reference/pricing/plans)).
- **Unmeasured.** The extra RAM and CPU for EmDash inside the site process was not measured (see §6).
- **Optional extras.** An email provider plugin (for magic links) and S3 media storage are optional. Cloudflare Workers Paid applies only to sandboxed plugins on Cloudflare.

### 3.8 Bot write APIs
- **REST API.**
  - REST lives under `/_emdash/api/*`.
  - Callers authenticate with a Bearer personal access token (PAT, prefix `ec_pat_`, created in the admin) or an OAuth token.
  - Tokens are "limited by their scopes and the associated user's role" ([E/reference/rest-api.mdx L24-30](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/reference/rest-api.mdx#L24-L30); [E/reference/mcp-server.mdx L21](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/reference/mcp-server.mdx#L21)).
  - Scopes include `content:read`/`write`, `media`, `schema`, `taxonomies`, `menus`, `settings`, `mcp:tools`, `transfer:*` and `admin`.
- **MCP server.** An MCP server is on by default and is turned off with `mcp: false` ([E/reference/configuration.mdx L425](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/reference/configuration.mdx#L425)).
- **CLI.**
  - `emdash content get` returns Markdown unless `--raw`.
  - `content create` and `update` take JSON through `--data`, `--file` or `--stdin`; `update` needs `--rev`, which works as optimistic concurrency.
  - Token resolution order: `--token`, then `EMDASH_TOKEN`, then stored credentials ([E/reference/cli.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/reference/cli.mdx)).
- **Typed client.** The client converts Markdown strings to Portable Text for `portableText` fields on writes ([E/packages/core/src/client/index.ts L874-910](https://github.com/emdash-cms/emdash/blob/913cb1b/packages/core/src/client/index.ts#L874-L910)).

### 3.9 Import and export (markdown, WordPress, Wiki.js)
- **WordPress.** Import comes from a WXR file or the EmDash Exporter plugin; `wordpress-rest` only probes ([E/migration/content-import.mdx L8-20](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/migration/content-import.mdx#L8-L20)).
- **Markdown.** There is no Markdown import UI. Markdown can be scripted in through the CLI or client (§3.8).
- **Wiki.js.** No importer found. The other importer packages are `contentful-to-portable-text` and `gutenberg-to-portable-text` (`E/packages/`).
- **Export.**
  - JSON backup, which is not restorable.
  - Seed export, which writes a SQLite file with `--with-content`.
  - Site package `.emdash`, through `emdash site export/import` (§1, §2).

### 3.10 Backup and restore
- **Recovery options.** The documented recovery paths are a raw database backup (`sqlite3 … ".backup"`), D1 Time Travel or a SQL dump, plus a separate copy of the media ([E/guides/backups.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/guides/backups.mdx)).
- **No JSON restore** (§2, row 3a).
- **Site package.** It moves content and schema into an *empty* site and excludes users, tokens, secrets and plugin data.

### 3.11 Maturity signals (as of 2026-10-05)
- **Repo size and activity.**
  - 13,408 stars; about 206 contributors by API pagination; the blog claims 175+ contributors and 1,800+ commits.
  - Last push 2026-10-05.
- **Open work and new reports.**
  - 162 open issues, 164 open PRs and 54 open `bug` issues.
  - 78 issues were opened since 1.0 shipped on 2026-09-28.
  - The "1.0" milestone shows 1 open and 162 closed (due 2026-09-28).
- **Release cadence.** 0.36.0 (09-01) to 0.42.0 (09-27), then 1.0.1 (09-28), then 1.1.0 (10-01). That is eight minor or major releases in five weeks. The breaking changes from 0.42 to 1.0 are listed in [E/upgrade-to-v1.mdx](https://github.com/emdash-cms/emdash/blob/913cb1b/docs/src/content/docs/upgrade-to-v1.mdx).
- **Stability label.** Semver for core packages starts at 1.0. The README "stable" text is dated 2026-10-05 (§2, row 4). The 1.0 post says: "we are just getting started".

## 7. Addendum: `theweekendprojects/emdash-better-auth` *(verified 2026-10-13 at [`59c2ad3`](https://github.com/theweekendprojects/emdash-better-auth/tree/59c2ad3))*

A third-party plugin that replaces EmDash's login with Better Auth. It is v0.12.2 on npm, MIT, created 2026-09-04, with 7 stars.

- **Issue #4 is not about Discord auth.** It is the design spike for multi-tenancy and organizations. Its "Discord" mentions refer to the EmDash community server. Its tenant-scoping discussion is relevant only indirectly, to per-club scoping.
- **No Discord provider is wired.** Providers are listed as data in `SOCIAL_PROVIDERS`. The plugin's `AGENTS.md` describes adding Discord as two lines. Wired today: Google, GitHub, Facebook, X and Cloudflare.
- **Blockers for our stack:**
  - **Cloudflare Workers only.** `src/providers.ts` and `src/route.ts` import `cloudflare:workers`. The README says "on Cloudflare Workers (D1 + R2). Other adapters are untested."
  - **Email verification.** `requireEmailVerification` defaults to `true` (`src/auth.ts:326`). Discord's `identify` scope returns no email.
  - **Roles.** New users get role 10, Subscriber (`src/emdash-adapter.ts:774`). There is no mapping from Discord roles to EmDash roles.
  - **Guild check.** Generic OAuth is configured with JSON in the `GENERIC_OAUTH_CONFIG` env var. JSON can't hold a function, so it can't express a guild check. Open issue #22, a server-side extension point for Better Auth plugins, would be the hook for one.
  - **Route clash.** It mounts Better Auth at `/api/auth`, where our reader auth would also sit.
- **Verdict.** It does not resolve Discord login for editors. The better route is EmDash's own `AuthProviderDescriptor`, modelled on `auth-atproto` (§3.4). It is runtime-neutral, needs no email, and lets our callback run the guild and role check. One Better Auth instance shared by readers and editors is a possibility for later, gated on Node support and #22. Reader gating is not a CMS selection criterion (handoff anti-goal), so this is not a reason to pick EmDash.
